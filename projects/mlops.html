MLOps Pipeline Simulation

View on GitHub

MLOps Pipeline Simulation is a fully local, cloud-inspired machine learning pipeline designed to demonstrate end-to-end MLOps architecture and orchestration principles — without relying on any paid cloud infrastructure.

The goal is not to optimise model accuracy, but to showcase the engineering mindset behind production-ready ML systems: reproducibility, modularity, versioning, monitoring, and deployment.

As a fun demonstration, the pipeline performs a simple dinosaur image classification task — but the core structure is designed to be task-agnostic and reusable across different ML domains.

Objectives

  • Build a reusable MLOps blueprint that mirrors real cloud pipelines using only local resources.
  • Demonstrate data ingestion, preprocessing, model training, versioning, and serving.
  • Simulate API gateways, orchestration, monitoring, and data storage layers.
  • Provide a realistic cloud-native architecture without cloud costs.

System Architecture

  • 🗄️ Object Storage: Simulates cloud buckets for storing raw uploads and preprocessed assets. Includes a file_log.csv manifest for tracking ingested files.
  • 🏢 Data Warehouse: SQLite3 database for structured metadata. Stores references to files, model versions, and logs. Includes init_db.py and schema.sql.
  • 🤖 ML Pipeline: Handles preprocessing (preprocess.py), training (train.py), hyperparameter config (hyperparams.py), prediction and evaluation (predict.py). Built with TensorFlow/Keras for modelling and scikit-learn/pandas for preprocessing. Modular and task-agnostic.
  • 📦 Model Registry: Stores and manages versioned models, tracks lineage and metrics for reproducibility.
  • 🚪 API Gateway: FastAPI services for server and client endpoints (server_api.py, client_api.py).
  • 🎛️ Orchestrator: Mimics Airflow/Prefect for scheduled retraining (retrain.py) and monitoring (monitor.py).
  • 🌐 Web Applications: Streamlit apps for server and client views (server_app.py, client_app.py).

Dataset Details

Sources:

  • Simple Dinosurus Dataset by cmglonly
  • Jurassic Park Dinosaurs Dataset by antaresl
  • Dinosaur Image Dataset (15 Species) by larserikrisholm

Huge thanks to the original authors for making these datasets publicly available!

I gathered these datasets together and meticulously cleaned the data by hand. This involved removing images with watermarks, text overlays, multiple species, any non-dinosaurs, and other problematic examples. Only high-quality, single-species dinosaur images made the cut and placed in object_storage/processed/ and object_storage/raw/ folders.

In the future, I plan to expand the dataset by hand-picking additional images to improve model accuracy and add more dinosaur classes, updating object_storage/ and the data warehouse as needed.

Fun fact: The original datasets included a suspicious number of pterosaurs—which, as any dino fan knows, is blasphemy to the name "dinosaur". (No flying reptiles allowed in this club!)

Example Client Workflow

This workflow describes the typical experience for an end user interacting with the system via the client app:

  1. Image Upload: The user uploads a single image through the client API. The image is stored in object_storage/raw/ and logged in the data warehouse.
  2. Preprocessing: The image is immediately preprocessed (cleaned, resized, etc.) and moved to object_storage/processed/.
  3. Prediction: The preprocessed image is passed directly to the trained model for inference. The predicted class (e.g. “Tyrannosaurus Rex”) and confidence scores are returned to the user via the client app.

Example Server Workflow

This workflow describes the developer or admin experience for managing and retraining the model via the server app:

  1. Bulk Upload: The developer uploads a .zip file containing multiple images through server_api.py. The images are extracted and stored in object_storage/raw/ and registered in the data warehouse.
  2. Preprocessing: The orchestrator (orchestrator/) triggers preprocessing for all new images, moving cleaned data into object_storage/processed/.
  3. Model Retraining: The orchestrator automatically starts a background job to retrain the model using the newly processed images. The updated model is versioned and saved to model_registry/.
  4. Monitoring: The server_app.py provides logs, metrics, and status updates on training jobs and system health.

Key MLOps Concepts Demonstrated

  • Reproducibility: Consistent results via structured data and model management in data_warehouse/ and model_registry/.
  • Automation: Simulated scheduling and async orchestration of training and monitoring tasks using orchestrator/ and monitor.py.
  • Modularity: Interchangeable components for storage (object_storage/), APIs (server_api.py, client_api.py), and models (model_registry/).
  • Versioning: Designed for traceable model lifecycle management in model_registry/ and the data warehouse.
  • Scalability Simulation: Mirrors real cloud workflows using lightweight local substitutes such as object_storage/, data_warehouse/, and orchestrator/.
